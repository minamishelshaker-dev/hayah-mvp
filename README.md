# حياة — MVP للعرض على المستثمرين

وساطة إلكترونية: تسجيل نزاع ← دعوة الطرف الثاني ← اختيار وسيط ← جلسات فيديو ← اتفاق تسوية بتوقيع الطرفين، مع مستندات مختومة بـ SHA-256 وسجل تدقيق متسلسل.

## التشغيل (15 دقيقة)

1. أنشئ مشروعًا على supabase.com.
2. طبّق قاعدة البيانات. الملفات في `supabase/migrations/` مرقّمة (من `…01_schema.sql` إلى `…11_settlement_sign_bound.sql`، **إحدى عشرة هجرة**) وتُنفَّذ **بالترتيب ومرة واحدة لكل منها**. العاشرة تضيف توقيع اتفاق التحكيم والحكم على المنصة وتغيّر صلاحيات الدوال الافتراضية، والحادية عشرة تربط توقيع تسوية الوساطة بالنص المعروض؛ لا تتجاوز أيًّا منهما: بـ Supabase CLI (`supabase link` ثم `supabase db push`) أو بلصقها واحدًا واحدًا في SQL Editor.
3. للعرض السريع فقط: عطّل «Confirm email» في **Authentication → Providers → Email**. **للتجربة الحقيقية فعّله** واتبع `docs/TRIAL_SETUP.md`.
4. انسخ `.env.example` إلى `.env.local` واملأ مفاتيح Supabase (من Project Settings → API). `DAILY_API_KEY` و`RESEND_API_KEY` اختياريان.
5. شغّل:
```bash
npm ci            # يتطلب Node 20.9 أو أحدث، ويثبّت الإصدارات المقفولة في package-lock.json
SEED_CONFIRM=yes npm run seed   # ينشئ حسابات العرض (بيئة تجريبية فقط). كلمة المرور عشوائية تُطبع مرة واحدة، أو حدّدها بـSEED_PASSWORD
npm run dev
```

## الاختبارات

```bash
npm run test:signing                  # فحص التوقيع الرقمي (لا يحتاج شيئًا)
npm run test:filesig                  # فحص توقيعات الملفات المرفوعة (يحتاج Node 22+)
npm run test:scan                     # قواعد فحص البرمجيات الخبيثة: متى يفشل مفتوحًا ومتى مغلقًا (يحتاج Node 22+)
PGUSER=postgres npm run test:db     # يحتاج PostgreSQL 15+ محليًا وصلاحية superuser
```
يبني قاعدة مؤقتة، ويطبّق كل ملفات `supabase/migrations/` بالترتيب، ثم يشغّل نحو 350 فحصًا آليًا تغطي الصلاحيات وبوابة الموافقة وتثبيت نسخة الاتفاقية والتوقيع وسجل التدقيق والمحاضر. الفحوص تعمل على **محاكاة** لأجزاء Supabase (`supabase/tests/stubs.sql`)، فلا تغني عن تجربة المسار كاملًا على مشروع Supabase حقيقي. لا توجد بعد اختبارات للواجهة.

## حسابات العرض

| الحساب | الدور |
|---|---|
| claimant@hayah.demo | مقدّم النزاع |
| respondent@hayah.demo | الطرف الثاني |
| mediator1@hayah.demo / mediator2@hayah.demo | وسطاء |
| admin@hayah.demo | مدير |

**المصادقة الثنائية:** حسابا المدير والوسطاء يُحوَّلان عند أول دخول إلى صفحة تسجيل تطبيق المصادقة (TOTP) ولا يعملان بدونها. للعرض السريع دون هاتف نفّذ في SQL Editor: `update app_settings set value = 'false' where key = 'require_mfa';` وأعده إلى `'true'` قبل أي تجربة حقيقية (التغيير مسجَّل في سجل التدقيق).

## التجربة المغلقة بحالات حقيقية

اتبع `docs/TRIAL_SETUP.md` (ضبط Supabase وVercel، بروفة، بروتوكول الحالات الأولى). أُضيف للتجربة:
- **بوابة موافقة:** شروط الاستخدام والخصوصية عند أول دخول، واتفاقية الوساطة لكل نزاع قبل فتح الملف. القبول مسجَّل بنسخة النص وبصمته والوقت وعنوان IP، وتفرضه قاعدة البيانات على كل إجراء (اقتراح وسيط، موافقة، قبول مهمة، جلسة، رفع مستند، توقيع).
- **النصوص القانونية بنسخ:** المدير ينشر النصوص من صفحة «النصوص القانونية»، والنصوص الحالية **مؤقتة** وتظهر تحذيرًا أحمر حتى تُستبدل.
- **تثبيت نسخة الاتفاقية لكل نزاع:** يُربط النزاع عند إنشائه بنسخة اتفاقية الوساطة السارية حينها، ولا يقبل أحد غيرها فيه، فلا يختلف الأطراف في النسخة.
- **حجب القراءة قبل القبول في قاعدة البيانات** (RLS): النزاع ومستنداته وجلساته واتفاقه وسجله وملفاته في التخزين لا تُقرأ قبل قبول الاتفاقية، ولو عبر استدعاء مباشر. قبل القبول لا يرى العضو إلا رقم الملف ونص الاتفاقية.
- **بصمة السجل الموسّعة (v2)** تغطي الفاعل والنزاع ونوع الكيان والحالة السابقة، وتُرسل بصمة آخر حدث يوميًا إلى بريدك (Vercel Cron) كنقطة تحقق خارج قاعدة البيانات، ويفحصها المدير من صفحة سجل التدقيق.
- **التحكيم (المرحلة أ) ومسار التصعيد من الوساطة:** ملف تحكيم منفصل لا ينقل شيئًا من الوساطة، بموافقة الطرف الآخر، واتفاق تحكيم يُوقَّع على المنصة (كلمة المرور + ختم المنصة) أو خارجها برفع المسح، ومحكّم منفرد بإقرار استقلال مكتوب (ولا يكون وسيط الملف السابق محكّمًا أبدًا)، وجدول إجرائي ومذكرات بمواعيد وجلسات فيديو، ومسودة حكم سرية للمحكّم يوقّعها على المنصة (كلمة المرور + الخطوة الثانية + ختم المنصة) أو ورقيًا فيُسجَّل مسح الحكم الموقَّع. التوقيع على المنصة بسيط وليس معتمدًا من ITIDA. **المنصة أداة لا جهة تحكيم، ولا تُصدر حكمًا قابلًا للتنفيذ.** التفاصيل والافتراضات القانونية في `docs/ARBITRATION.md`.
- **إشعارات بالبريد** (Resend) عند كل حدث يحتاج انتباهًا: قبول الدعوة، واقتراح الوسيط والموافقة عليه وقبوله، وجدولة جلسة، وفتح الاتفاق للتوقيع أو إعادة فتحه، واكتمال التوقيع، وانتهاء الملف، وانسحاب الوسيط. الرسالة لا تحمل تفاصيل النزاع أبدًا. ولوحة المستخدم تعرض قسم «ينتظرك» لكل ما ينتظر إجراءً منه عبر كل ملفاته.
- **إعادة فتح مسودة الاتفاق** للتعديل ما دام لم يوقّع أحد (بعد أول توقيع يُقفل النص نهائيًا).
- **توقيع رقمي للمحاضر (Ed25519):** إذا ضُبط `RECORD_SIGNING_PRIVATE_KEY` يوقّع الخادم كل محضر يصدر، ويمكن لأي جهة فحصه **دون الرجوع إلى المنصة** بالمفتاح العام (`/api/record-key`) وملف «تنزيل مع التوقيع» وسكربت `scripts/verify-record.mjs`. التحقق في صفحة `/verify` يفحص التوقيع أيضًا. ولد المفتاح بـ `npm run gen:signing-key`.
- **الخط محلي** (Cairo من الحزمة نفسها، لا طلبات إلى Google).
- **حدّ الثقة:** كل ما يُنتج دليلًا (تسجيل المستند، التوقيع، قبول الاتفاقيات) لا يكتبه إلا الخادم، عبر دوال لا يستدعيها مستخدمو الـAPI: لا يمكن إدراج صف مستند بلا ملف حقيقي في التخزين، ولا التوقيع دون خطوة كلمة المرور، ولا اختيار عنوان IP المحفوظ مع التوقيع. الأفعال مسجّلة باسم فاعلها الحقيقي. **يلزم لذلك ضبط `SUPABASE_SERVICE_ROLE_KEY` على الخادم.**
- **لا صفوف خام للأعضاء:** عناوين IP والمتصفح والبريد والهاتف والرموز لا تُقرأ عبر الـAPI إلا لصاحبها وللمدير؛ ما يراه الأعضاء الآخرون عبر دوال تعرض حقولًا مسموحة فقط (السجل الزمني، حالة القبول، التوقيعات، أسماء الأطراف، دليل الوسطاء). دليل الوسطاء لا يعرض إلا من رقّته الإدارة **وتحقق من هويته**.
- **حدود وحماية:** حد يومي للدعوات (10)، وتحديد معدل الطلبات على الدخول والتسجيل واستعادة كلمة المرور والتحقق العام والرفع وتوكن الجلسة، وقائمة أنواع ملفات مسموحة (PDF وصور وWord وExcel ونص)، ورؤوس أمان (CSP في وضع التقرير فقط حتى تختبر الفيديو)، وتوكن الجلسة لا يصدر لجلسة ملغاة أو ملف منتهٍ ويُفتح قبل الموعد بربع ساعة.
- **التحقق بخطوتين (TOTP) للمدير والوسطاء، تفرضه قاعدة البيانات:** الجلسة التي لم تجتز الخطوة الثانية لا تملك أي صلاحية مدير أو وسيط، حتى باستدعاء مباشر (لا قراءة ملفات، ولا جدولة، ولا صياغة اتفاق، ولا مؤشرات). الأطراف لا يُطلب منهم شيء. لا يُحبس المدير الجديد خارج النظام لأنه يصل إلى صفحة التسجيل بجلسة الخطوة الأولى. المدير يرى حالة التحقق لكل مدير ووسيط ويعيد تعيينه عند فقدان الهاتف، وكل إعادة تعيين مسجَّلة قبل تنفيذها.
- **مسارات الفشل:** رفض الدعوة من رابطها، وسحب النزاع قبل تسلّم وسيط له، وتجديد الدعوة أو تصحيح بريد الطرف الثاني، وانسحاب الوسيط واختيار بديل (يفقد الأول كل وصول وتُلغى جلساته القادمة)، وإنهاء الوساطة دون تسوية من أي طرف، وإغلاق الملف بعد التسوية. كل ملف ينتهي بنتيجة مسجَّلة (تسوية، دون تسوية، سحب، رفض) وسبب اختياري، ثم يصبح للقراءة فقط: لا مستندات ولا جلسات ولا تعديل.
- **صفحة المؤشرات** للمدير: مسار النزاعات، والأزمنة، والقيم، وجاهزية التجربة.
- **تأكيد البريد واستعادة كلمة المرور** تعملان عبر `/auth/callback` (يجب فتح الرابط من نفس المتصفح الذي طُلب منه).
- **محضر موثّق** لكل نزاع: لقطة ثابتة تُبنى داخل قاعدة البيانات وتُحفظ ولا تُعدَّل (الأطراف، قبول الاتفاقيات، المستندات وبصماتها، الجلسات، الاتفاق والتوقيعات، السجل الزمني، نتيجة فحص السلامة). تُطبع/تُحفظ PDF من المتصفح، وتُنزَّل JSON.
- **صفحة تحقق عامة** `/verify`: يدخل أي شخص بصمة المحضر أو يرفع ملف JSON، فيعرف هل صدر عن المنصة ولأي نزاع ومتى. لا تكشف غير رقم النزاع وتاريخ الإصدار.

## سيناريو العرض (10 دقائق، استخدم نافذتين خاصتين للمتصفح)

1. **مقدّم النزاع:** نزاع جديد (قيمة بين 50 و500 ألف) ← انسخ رابط الدعوة.
2. **الطرف الثاني:** افتح الرابط ← دخول ← قبول الدعوة.
3. أي طرف يقترح وسيطًا ← الطرف الآخر يوافق ← **الوسيط** يقبل.
4. ارفع مستندًا ثم اضغط «تحقق من السلامة».
5. **الوسيط:** جدولة جلسة ← دخول الجلسة (وضع عرض بدون Daily، فيديو حقيقي معه).
6. **الوسيط:** صياغة الاتفاق ← فتح للتوقيع ← **الطرفان** يوقّعان بكلمة المرور.
7. **المدير:** سجل التدقيق ← «فحص سلامة السلسلة».

## ما تغيّر عن المواصفات الأصلية (ولماذا)

- **الأدوار:** الجميع يبدأ «طرف»، والمدير وحده يرقّي إلى وسيط/محامٍ. (المواصفة الأصلية كانت تسمح لأي مستخدم بتسجيل نفسه مديرًا.)
- **كل التعديلات عبر دوال في قاعدة البيانات** تتحقق من هوية المنفّذ؛ المستخدم لا يكتب في الجداول مباشرة.
- **سجل التدقيق** تكتبه triggers داخل قاعدة البيانات وليس كود التطبيق، في سلسلة بصمات، ولا يقبل UPDATE/DELETE.
- **رفع الملفات** من المتصفح مباشرة إلى التخزين (حد Vercel للطلب نحو 4.5 م.ب)، ثم يعيد الخادم حساب البصمة ويقارنها.
- **التوقيع:** توقيع بسيط داخل المنصة (إعادة إدخال كلمة المرور + بصمة النص + الوقت وعنوان IP) بدل SignNow، لأن واجهة SignNow في المواصفة لا تعمل كما كُتبت.
- **فيديو:** غرف Daily خاصة بـ meeting tokens، **والتسجيل مغلق** حفاظًا على سرية الوساطة.
- **حُذف من النطاق:** المدفوعات، رفع صور الهوية والرقم القومي (تقليلًا للبيانات الحساسة)، OTP، Sentry، لوحة الوسيط الشخصية، جدول `dispute_parties`.
- مكوّنات الواجهة مكتوبة يدويًا بـ Tailwind بدل أمر `shadcn init` التفاعلي، ويمكن إضافة shadcn لاحقًا.

## قبل أي استخدام فعلي (ليس عرضًا)

- التوقيع هنا **ليس** توقيعًا إلكترونيًا مرخّصًا من ITIDA؛ راجع قانون التوقيع الإلكتروني 15 لسنة 2004 واشتراطاته قبل الاعتماد عليه في الإثبات.
- قالب اتفاق التسوية استرشادي ويحتاج مراجعة محامٍ.
- النصوص القانونية الثلاثة مؤقتة حتى تنشر نصوصك المعتمدة من صفحة «النصوص القانونية».
- استضافة Supabase/Vercel/Daily خارج مصر: راجع متطلبات قانون حماية البيانات الشخصية 151 لسنة 2020.
- المحضر والتحقق يثبتان صدور المحضر وسلامة محتواه كما صدر، لا صحة وقائع النزاع، ولا يغنيان عن توقيع مرخّص. (قانوني: قيمته في الإثبات تقدّرها أنت.)
- الاختبارات الآلية تغطي قاعدة البيانات فقط وعلى محاكاة لـ Supabase؛ لا اختبارات للواجهة. يوجد ملف CI (`.github/workflows/ci.yml`) لكنه لم يُشغَّل بعد، ولا يمنع الدمج عند فشله ما لم تفعّل حماية الفرع في المستودع. ولم تُجرَّب المنصة على مشروع Supabase حقيقي ولا من متصفح.
- فعّل ترقية الحسابات يدويًا، ولا تضع بيانات عملاء حقيقية قبل مراجعة أمنية مستقلة.

## النشر على Vercel

ارفع المشروع إلى GitHub، استورده في Vercel، وأضف نفس متغيرات `.env.local` (واجعل `NEXT_PUBLIC_APP_URL` رابط الموقع)، ثم Deploy.

## ما أُضيف بعد التقييم الشامل

- **CI** (`.github/workflows/ci.yml`): typecheck وبناء واختبارات التوقيع والملفات واختبارات قاعدة البيانات على PostgreSQL، وفحص يمنع وصول مفتاح الخدمة إلى ملفات المتصفح.
- **فحص محتوى الملفات المرفوعة** (`lib/filesig.ts`): يتأكد الخادم أن بايتات الملف تطابق نوعه المعلن. وخطاف اختياري لفاحص برمجيات خبيثة خارجي: `MALWARE_SCAN_URL` (+ `MALWARE_SCAN_TOKEN`، و`MALWARE_SCAN_REQUIRED=true` لرفض الرفع عند تعذّر الفحص).
- **CSP**: اضبط `CSP_ENFORCE=true` في Vercel بعد اختبار كامل ليبدأ الحجب فعليًا (يبقى `unsafe-inline`).
- **سجل نظر المدير**: كل اطلاع من المدير على نزاع أو تحكيم يُسجَّل (مرة في الساعة لكل ملف) ويظهر للأطراف في سجلهم الزمني.
- **أمان الدوال**: الدوال الجديدة لا تُمنح لـanon/authenticated افتراضيًا، وفحص آلي يتأكد أن كل دالة خادم لا يستطيع المستخدم تنفيذها.
- **مراقبة الأخطاء**: `instrumentation.ts` يكتب كل خطأ طلب كسطر JSON في سجلات Vercel، وصفحتا خطأ بالعربية. لـSentry: `npx @sentry/wizard@latest -i nextjs`.
- **حسابات العرض**: لم تعد كلمة مرورها في المستودع، ولا يعمل السكربت دون `SEED_CONFIRM=yes`.


تحديث آلي: تفعيل سير استخراج ملفات المشروع والتحقق من النشر.
